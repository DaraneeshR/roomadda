01 — MVP OverviewRoomadda · 1.5 Month Plan

Section 01

MVP Overview
& Goals

The MVP (Minimum Viable Product) of Roomadda must prove one core thing: a student or working professional can open the app, find a verified PG, pay a token, and confirm a booking — end to end — without a single phone call. Everything else in this MVP supports or enables that one outcome.

🎯
North Star for MVP
A user in Bangalore can search for a PG near their office, view photos and amenities, book a room by paying ₹1,000 online, receive a confirmation on WhatsApp, and the PG owner gets notified instantly — all within 5 minutes, all on their phone. This is the single experience the MVP must nail perfectly.

Languages in MVPEnglish only. Hindi/regional in Phase 2.
Definition of DoneAll P0 features built, tested, deployed to staging, bug-free on both iOS and Android, admin panel live, at least 3 end-to-end test bookings completed on staging before release.
⚠️
Important Framing for Agency
This is a PG accommodation platform — NOT a real estate or property sales portal. The terminology throughout must reflect this: tenants (not buyers), hosts (not sellers), PG listings (not properties for sale), monthly rent (not property price), token payment (not down payment). This distinction must be reflected in every screen, every database model, and every API endpoint.

03 — User / Tenant AppRoomadda · 1.5 Month Plan

Section 03

User / Tenant
Mobile App

The consumer-facing app for students and working professionals. This is the most polished, most tested, most important part of the MVP. Every screen must feel fast, clean, and trustworthy. The entire journey — from search to booking confirmation — must be completable in under 5 minutes.

🚀
3.1 — Onboarding & Registration
First-time experience and account creation
Mobile OTP Registration & Login
User enters Indian mobile number → receives OTP via SMS → verified and logged in. OTP expires in 5 minutes. Max 3 OTP attempts before 10-minute lockout. After first login, user can enable biometric authentication (Face ID / fingerprint) for future logins. The OTP screen must have a 60-second resend timer.
  • OTP delivered within 10 seconds via MSG91 or Twilio
  • Invalid OTP shows clear error — does not reveal if number exists
  • Biometric toggle visible in profile settings after first login
  • Session persists for 30 days unless manually logged out
UserP0 Core
Google Sign-In
One-tap Google account authentication. On first Google login, the app collects the mobile number (with OTP verification) since it's needed for WhatsApp notifications and host contact. Google login is linked to OTP login — both point to the same account if the mobile number matches.
  • Google login does not bypass mobile number requirement
  • If same mobile used for Google + OTP — accounts merge, not duplicate
UserP0 Core
Profile Setup
After registration: Full name, profile photo (optional at signup), gender (Male / Female / Prefer not to say — used for gender-specific PG filters), date of birth, city of interest, and occupation type. If Student → college name + city. If Working Professional → company name + work location. Occupation type is saved and used to auto-fill search defaults. Profile can be completed later but is required before making a booking.
  • Profile completion shown as a progress indicator
  • Incomplete profile prompts user on home screen with a non-blocking banner
  • Gender field is used for PG gender-filter matching — not displayed to hosts
UserP0 Core
KYC Document Upload
Required before payment is processed for any booking. User uploads: Aadhaar card (front + back photo). Plus one supporting ID: Student ID card (for students) or Office ID / Offer Letter (for working professionals). Photos uploaded to secure cloud storage. Admin reviews and approves in admin panel. Status shows: Not Submitted / Pending Review / Verified / Rejected. Booking initiation is allowed before KYC approval, but payment is blocked until status is Verified.
  • Upload supports camera capture or gallery pick
  • Files compressed to max 2MB before upload — no quality loss visible
  • Rejected KYC shows specific reason and allows re-upload
  • KYC documents stored encrypted, only admin can view them
UserP0 Core
Trusted Contacts (Safety Feature)
User adds 1–3 trusted contacts (name + mobile number). These are stored in the app. A visible SOS button on the main dashboard silently shares the user's current GPS location via SMS to all trusted contacts and sends an alert to RA Admin. The SOS button must be accessible within 2 taps from anywhere in the app. Must work even with poor connectivity (SMS fallback).
  • SOS button visible on home dashboard at all times
  • Trusted contacts setup prompted during onboarding for female users
  • SOS sends SMS (not just app notification) for reliability
UserP0 Core
🔍
3.2 — Search & Discovery
Finding the right PG quickly
Location-Based Search with Autocomplete
Search bar on home screen. Powered by Google Places API for autocomplete. Accepts: locality name, landmark, college name, metro station, or company name. The search resolves the entered query to GPS coordinates and shows all PGs within a configurable radius (default 3km, user can expand). Also supports "Near Me" using device GPS. Recent searches saved locally (last 5).
  • Autocomplete results appear within 300ms of typing
  • College names resolve to coordinates via Places API
  • "Near Me" requests GPS permission only once — remembered
  • Empty state on search shows recent searches + popular cities
UserP0 Core
Advanced Filters
Filter panel accessible from search results. Filters: Rent range (₹3,000–₹30,000 slider), Room type (Single / Double / Triple sharing), Gender (Boys / Girls / Co-ed), Meals included (Yes / No), Amenities multi-select (WiFi, AC, Geyser, Laundry, Parking, CCTV, Power Backup, Gym, Study Table), Furnishing (Fully furnished / Semi / Unfurnished), Verified only (toggle — shows RA-verified PGs only), Move-in date (date picker — shows PGs available on that date). Active filters shown as removable chips above results. Filter state persists during the session.
  • Filter results update in real-time as sliders move
  • Number of matching PGs shown on the filter button
  • "Clear all filters" resets to default state
  • Gender filter auto-set from user's profile gender — can be manually changed
UserP0 Core
Search Results — List View
Each listing card shows: Cover photo (swipeable thumbnails on card), property name, locality + distance from searched location, rent starting from (per month), key amenity icons (3–4 most relevant), room types available as tags, Verified badge (if admin-verified), Featured badge (if featured). Cards sorted by: Relevance (default), Price Low→High, Price High→Low, Distance, Newest. Infinite scroll — loads 15 at a time. Pull-to-refresh supported.
  • Results load within 1.5 seconds for up to 50 listings
  • Skeleton loaders shown during fetch — no blank screen
  • Featured listings pinned to top 2 positions, clearly labeled
  • No results state shows "Expand search radius" suggestion
UserP0 Core
Map View Toggle
Toggle between list view and map view. Map shows all matching PGs as pins. Tapping a pin shows a mini-card (photo + name + rent + distance). Tapping mini-card opens full detail page. Map uses Google Maps SDK. Pins are clustered when zoomed out — expand on zoom in. Map re-searches automatically when user pans significantly (with "Search this area" button).
  • Map initialises centred on searched location
  • Cluster count shown on grouped pins
  • Current device location shown as a blue dot
UserP0 Core
PG Detail Page
Full listing page with: Swipeable photo gallery (full-screen expand on tap), property name + locality + verified badge, distance from searched location, room-wise pricing table (room type / occupancy / rent / deposit / availability), all amenities with icons, house rules (listed clearly), meals info (which meals, veg/non-veg), host profile card (name, photo, response rate — no phone number), Google Maps embed showing property location, "Book Now" and "Add to Wishlist" CTAs always visible at bottom. For multiple room types — user selects before proceeding to booking.
  • Photo gallery supports pinch-to-zoom
  • "Book Now" disabled and shows reason if: no rooms available, user's KYC pending, or move-in date not selected
  • Share button generates a deep link to the listing
  • Back to results preserves scroll position and filters
UserP0 Core

3.3 — Booking Flow
The single most critical user flow — must be flawless
Booking Initiation
From the detail page, user taps "Book Now". A bottom sheet slides up with: selected room type (changeable), move-in date picker (blocks past dates and already-booked dates), meal plan selection (if PG offers meals: included / not required), booking summary — room type, rent per month, security deposit, token amount to pay now. User reviews and taps "Proceed to Pay." If the PG has "Instant Book" enabled — booking is confirmed on payment. If not — host must approve within 24 hours before payment link activates.
  • Move-in date defaults to the earliest available date
  • Booking summary clearly distinguishes token (paid now) from rent (monthly)
  • Cancellation policy shown before payment
  • Double-booking prevented at database level — not just UI
UserP0 Core
Token Payment
User pays a token amount (set per listing, e.g. ₹500–₹2,000) to confirm the booking. Payment options: UPI (PhonePe, GPay, Paytm, any UPI ID), Debit/Credit card, Net banking. Powered by Razorpay. On successful payment: booking status changes to Confirmed, user sees a success screen with Booking ID, WhatsApp message sent to user and push notification to host. Token is adjusted against first month's rent. Token is non-refundable if user cancels within 48 hours of move-in.
  • Payment timeout of 10 minutes — expired sessions show clear error
  • Payment failure shows reason and allows retry without re-entering booking
  • Success screen shows: Booking ID, PG address, host name, move-in date
  • PDF booking confirmation downloadable from success screen
UserP0 Core
Booking History & Status Tracking
A "My Bookings" tab shows all bookings — active, past, pending, cancelled. Each booking card shows: PG name + photo, booking status, room type, move-in date, monthly rent, token paid. Statuses: Pending Host Approval / Payment Pending / Confirmed / Active Stay / Completed / Cancelled. Tapping a booking shows full details, payment history, and available actions (cancel if within policy, contact host).
  • Booking status updates in real-time via push notification
  • Cancelled bookings retained in history — not deleted
UserP0 Core
Wishlist / Saved PGs
Heart icon on every listing card and detail page. Wishlisted PGs saved to user's account (persists across devices). A dedicated Wishlist tab shows all saved PGs. Wishlisted PGs show "Available" or "Full" status in real-time. User gets push notification if a wishlisted PG drops rent or has a new room available.

3.4 — Tenant Dashboard (Post Move-In)
Daily-use features that keep tenants engaged with the app
Home Dashboard — Active Stay View
Once a user's move-in date is reached, the home screen transforms into a Tenant Dashboard. Shows: PG name, room number, move-in date, monthly rent, next rent due date, host name, SOS button (always visible), quick action cards (Pay Rent, Raise Request, View Menu, Chat with Host). A leave notice section shows "Notice served / not yet served." Navigation bar changes to show: Home, Menu, Service, Chat, Profile.
  • Dashboard activates automatically on move-in date — no manual trigger
  • SOS button visible in top-right of every screen during active stay
UserP0 Core
Daily Meal Menu View
Only visible if the PG provides meals. Shows today's menu: Breakfast / Lunch / Dinner with dish names. If a meal is not provided for a slot, shows "Not available today." Scroll right to see tomorrow's menu (if host has entered it in advance). Host name and last-updated time shown at bottom of menu card for transparency.
  • Menu refreshes automatically at midnight
  • If host hasn't updated menu for today — shows "Menu not updated yet" with timestamp of last update
UserP0 Core
Monthly Rent Payment
Tenant sees current month's rent status: Paid / Due / Overdue. Tapping "Pay Rent" opens Razorpay with the exact amount pre-filled. After payment: status changes to Paid, receipt generated, push notification to host. Payment history shows all past rent payments with date, amount, transaction ID, and downloadable receipt. Overdue rent shown in red with the number of days overdue.
  • Rent payment via UPI, card, net banking — same gateway as token
  • Partial payment NOT allowed — must pay full month's rent
  • Receipt PDF shows: PG name, tenant name, room, month, amount, transaction ID
UserP0 Core
Service Request — Raise Maintenance Issue
Tenant raises a request from the Service tab. Form fields: Category (Electrical / Plumbing / Internet / Furniture / Cleanliness / Other), Description (text, required), Priority (Urgent / Normal), Photo (optional, max 3). After submission: request assigned a ticket number, host notified via push notification. Status tracking in-app: Submitted → Acknowledged → Resolved. Tenant can add follow-up comments. Urgent requests not resolved in 4 hours auto-escalate to admin.
  • Tenant cannot delete a submitted request — only admin can
  • All requests visible to admin for quality monitoring
  • Resolved requests prompt a quick 1–5 star satisfaction rating
UserP0 Core
In-App Chat — Tenant ↔ Host
Dedicated chat channel between tenant and their current PG host. Standard text messaging with photo sharing. No voice or video in MVP. Messages delivered in real-time. Offline messages queued and delivered when reconnected. Typing indicators shown. Chat history persists. Host's business hours shown — "Typically replies within X hours" auto-computed from response data. All chats are logged and visible to admin.
  • No phone numbers shared through chat — stays in-app
  • Chat unavailable for cancelled bookings
  • Offensive content reporting available on long-press of any message
UserP0 Core
Leave Notice Submission
Tenant can submit a leave notice from their dashboard. Enter intended move-out date (must be at least notice period days from today — defined per PG). Once submitted: host is notified, admin is notified, the room is queued as "Vacating Soon" in inventory. Tenant cannot withdraw notice within 3 days of move-out date. Leave notice date and status shown on tenant dashboard.

04 — Host / PG Owner AppRoomadda · 1.5 Month Plan

Section 04

Host / PG Owner
Mobile App

The supply-side app used by PG owners to list and manage their properties. Hosts may have limited tech experience — the UI must be exceptionally simple and task-oriented. Hosts use this every single day, so speed and reliability are critical.

📝
4.1 — Host Onboarding & Property Listing
Host Registration & KYC
Separate registration flow — host taps "List Your PG" from the app or promotional website. Collects: full name, mobile number (OTP verified), email, Aadhaar or PAN card upload, property ownership proof (electricity bill, rent agreement, or ownership deed). After submission — RA Admin reviews and activates the host account. Host receives SMS + email when approved. Until approved, host can complete the listing form but the listing goes live only after admin approval.
  • Host and user are separate roles — same mobile number cannot be used for both
  • Host account creation does not require app download — web flow available
HostP0 Core
Property Listing Creation — Guided Form
Step-by-step form with progress indicator. Step 1 — Basics: Property name, full address, Google Maps pin (drag to exact location), PG type (Boys / Girls / Co-ed). Step 2 — Rooms: For each room type (Single / Double / Triple), enter: number of rooms, monthly rent, security deposit, furnishing (Fully / Semi / Unfurnished), bathroom type (attached / shared). Host adds as many room types as needed. Step 3 — Amenities: Checkbox grid of all amenities. Step 4 — Meals: Does PG offer meals? If yes — which meals (Breakfast / Lunch / Dinner), type (Veg / Non-Veg / Both). Step 5 — House Rules: Visitor policy, curfew time, smoking/drinking allowed, notice period (days). Step 6 — Photos: Minimum 5 photos required. Camera capture or gallery. Each photo shows a label suggestion (e.g. "Add exterior photo"). Step 7 — Token & Booking: Token amount (₹500–₹5,000), booking type (Instant Book / Request to Book).
  • Form saves draft at every step — host can resume later
  • Minimum 5 photos enforced — cannot submit without them
  • Address validated against Google Maps — pin must be manually confirmed
  • Submitted listing goes to admin queue — not live immediately
HostP0 Core
Edit Listing Details
Host can edit any field of their listing post-approval. Minor edits (photos, amenities, meal info) go live immediately. Major edits (rent changes above 20%, address change) require re-approval by admin. An edit history log is maintained. Host can pause a listing (makes it invisible to users without deleting it — useful for renovation or full occupancy periods).
  • Paused listings shown to host with "Paused" badge — invisible to users
  • Admin notified of major edits for review
HostP0 Core
📦
4.2 — Inventory & Booking Management
Daily Inventory Update
Host dashboard shows current room inventory for each room type: Total rooms / Occupied / Available. Host can adjust the available count per room type — this is specifically for walk-in tenants who were manually added. Regular app bookings auto-update inventory. The system recommends auto-inventory based on bookings (host can override). If all rooms of a type are marked full, users see "Fully Occupied — Join Waitlist" for that type.
  • Inventory auto-updates on every confirmed booking and check-out
  • Manual override clearly flagged with a different colour in admin
  • Host gets a daily reminder to verify inventory if it hasn't been touched in 3 days
HostP0 Core
Booking Request Management
For "Request to Book" listings: incoming requests appear in a Bookings tab with 24-hour countdown timer. Host sees: tenant name (after accepting), room type, move-in date, and can Accept or Decline with optional reason. Accepting sends a payment link to the tenant. If host doesn't respond in 24 hours, the request auto-expires and the tenant is notified. For Instant Book listings — bookings appear in the confirmed tab directly.
  • Accepting a request locks that room for 4 hours while tenant pays
  • If tenant doesn't pay in 4 hours, room is released and request cancelled
  • Host cannot see tenant's KYC documents — only name and booking details
HostP0 Core
Walk-In Booking Entry
When a tenant arrives directly without booking through the app, host manually creates a record: tenant name, mobile number, Aadhaar number (entered by host, not uploaded), room type, room number, move-in date, rent agreed, security deposit collected, payment mode (Cash / UPI). System sends an SMS invite to the tenant's number to download Roomadda and link their stay. Walk-in bookings are flagged differently in analytics.
  • Walk-in bookings auto-reduce available room count
  • SMS invite contains a deep link to app download + pre-filled mobile number
HostP0 Core
Tenant Roster
Host sees a list of all current tenants. For each tenant: name, room type + room number (if assigned), move-in date, monthly rent, current rent status (Paid / Due / Overdue), and a button to open their in-app chat thread. Past tenants visible in a separate "Past Tenants" tab with move-out date and stay duration. No sensitive KYC information shown to host.
  • Overdue tenants shown in red at the top of the list
  • Host can mark a tenant as checked out from this view
  • Each tenant row is not expandable to show others' data
HostP0 Core

Meal Menu Update
From the Operations tab, host updates today's meal menu. Three sections: Breakfast / Lunch / Dinner. Each accepts a free-text description (e.g. "Idli, Sambar, Chutney"). Toggle to mark a meal as "Not available today." Host can also update tomorrow's menu in advance. Weekly templates — host can save a template (e.g., "Standard Monday Menu") and apply it to any day to avoid re-typing the same menus each week.

All open service requests from tenants shown in a prioritised list. Urgent requests at top in red. Each request shows: tenant name, room number, category, description, submitted time, current status. 05 — Field Agent AppRoomadda · 1.5 Month Plan

Section 05

Field Agent
Mobile App

A lean, task-oriented mobile app for Roomadda's on-ground agents. Agents visit PGs, verify listings, and help users book. The app must work well on patchy connectivity — agents are often in buildings with weak signals.

ℹ️
Agent App Note
The agent app can share the same mobile app binary as the user and host apps, with role-based routing on login. However the agent interface must be completely distinct — different navigation, different dashboard, different feature set. Agents are created by admin — they cannot self-register. Agent accounts are activated only by RA Admin.
Agent Dashboard — Today's Tasks
Home screen shows today's assigned visits in order, a count of pending assisted bookings, and a summary of bookings closed this month. Simple, clean — optimised for quick action, not data browsing. Offline mode shows last-synced data with a banner indicating connectivity status.
AgentP0 Core
Property Visit Assignment & Check-In
Admin assigns property visits to agents from the admin panel. Each visit shows: property name + address, host contact name, scheduled date/time, and reason for visit. Agent taps "Start Visit" which triggers a GPS check-in (records lat/long at time of tap — must be within 200 metres of the property address to validate visit). If agent is not within range, they can flag "Cannot reach property" with a note.
  • GPS check-in timestamp and coordinates saved to visit record
  • Admin sees check-in location on a map in the admin panel
  • Agent cannot complete inspection without GPS check-in
AgentP0 Core
Property Inspection Checklist
Structured checklist the agent fills during the visit. Sections: Amenity Verification (each amenity claimed in the listing is checked Yes/No/Partial — e.g., "WiFi working?" / "AC functional?" / "Geyser works?"), Room Count Verification (actual room count vs listed), Cleanliness (1–5 rating per area: rooms, bathrooms, kitchen, common areas), Security Infrastructure (CCTV presence, gate lock, security guard), Discrepancies (free text — any mismatch between listing and reality), Overall Recommendation (Approve / Approve with Conditions / Reject), Notes for admin (free text). Minimum 8 photos required — taken within the app.
  • Photos taken in-app are geotagged and timestamped
  • Checklist cannot be submitted without minimum photos
  • Submitted reports go directly to admin's review queue
  • Partial saves supported — agent can pause and resume on the same visit
AgentP0 Core
Assisted Booking Flow
After accompanying a user on a property visit, if the user wants to book, the agent initiates from their app: selects the property, room type, move-in date, enters the user's name and mobile number. The system sends a WhatsApp + SMS payment link to the user's phone. The user taps the link, opens Razorpay, pays the token from their own device. Booking is linked to the agent's account for commission tracking. The agent can see the status of pending payment links (sent, paid, expired).
  • Payment link valid for 2 hours — expired links shown clearly
  • Agent cannot make the payment on the user's behalf — user must pay
  • Booking attribution to agent is automatic and immutable once confirmed
AgentP0 Core
Walk-In Booking Entry (Agent Version)
If an agent is at a property and a walk-in user wants to book, agent records: user details, room type, move-in date. Collects token payment via a Razorpay QR code shown on screen (user scans with their UPI app). On payment success, booking is created, receipt generated as a shareable PDF. This walk-in booking is tagged as "Agent Walk-In" for commission and analytics.
  • QR payment auto-confirms once Razorpay webhook fires
  • Agent's commission on walk-in bookings identical to assisted bookings
AgentP0 Core
Agent Monthly Performance Summary
Simple view showing: visits completed this month, bookings closed (assisted + walk-in), commission earned this month, payout status (Pending — manual for MVP). No complex analytics in MVP — just the numbers agents need to track their own performance.

06 — RA Admin PanelRoomadda · 1.5 Month Plan

Section 06

RA Admin
Web Panel

The internal command centre — accessible only via web browser, only to Roomadda team members. Must be functional and fast, not beautiful. Designed for desktop use by ops and support staff. All data in the system is visible here. All approvals happen here.

🚫 Hard Rule — No Booking Capability

RA Admin accounts are completely restricted from initiating, approving, or making any booking on behalf of any user. This must be enforced at the backend API level — not just hidden in the UI. Any API request with an admin role token to the booking creation endpoint must return a 403 Forbidden response.
Admin accounts have a separate login URL (admin.roomadda.com). The admin panel is NOT accessible from the consumer mobile app in any way.
Admin actions are logged with: action type, timestamp, admin user ID, affected entity (user/host/listing/booking ID). This audit log is immutable and only accessible by Super Admin role.
Listing Approval Queue
Every new property listing submitted by a host appears here. Admin sees: listing details, all photos, host KYC status, and the agent inspection report (if a visit was done). Admin actions: Approve (listing goes live immediately), Approve with Edit Request (sends specific feedback to host — listing does not go live until host resubmits), Reject (with mandatory reason — host can resubmit after fixes). Approval/rejection triggers email + SMS to host. SLA target: review within 48 hours of submission.
  • Listings older than 48 hours without action highlighted in orange

Payment Gateway Requirement
Razorpay is the recommended gateway. It supports UPI, cards, net banking, payment links, QR codes, webhooks, and refunds all under one integration. The agency must implement Razorpay webhooks for payment success/failure events — do NOT rely on the redirect callback alone, as users can close the app before the callback fires. All payment-related data must be stored server-side, never in the mobile app's local storage.
⚠️
Payout & Escrow Note
In the MVP, Roomadda collects all payments (token + rent) and manually transfers to hosts after deducting commission. This is acceptable for early operations with low transaction volumes. By Phase 2, Razorpay Route (split payment / marketplace settlement) must be implemented to automate payouts. The agency must design the database model to support automated payouts from day one — even if the automation is wired up in Phase 2.
09 — Business & Privacy RulesRoomadda · 1.5 Month Plan

Section 09

Business &
Privacy Rules

These are non-negotiable constraints that must be implemented at the backend — not just hidden in the UI. Every rule here is a product or legal requirement.

🔒 Privacy Rules — Non-Negotiable

No tenant can see any other tenant's name, room, payment info, or contact details — even if they are in the same PG. The database query for tenant roster must be filtered by tenantId = currentUser and propertyId = currentProperty. Never return all tenants to a tenant-role API call.
Hosts can see their tenants' name, room, move-in date, rent status, and contact number. They cannot see KYC documents, payment card details, or any admin-level data.
Agents can only see data for leads and properties assigned to them. An agent for Bangalore cannot query users or listings in Delhi. Zone-based data access enforced at API level.
KYC documents (Aadhaar photos, ID proofs) are stored encrypted (AES-256 at rest). Access is via signed URLs valid for 30 minutes only. Only admin-role API tokens can generate these signed URLs.
No raw phone numbers are shared between users and hosts in chat. All communication routes through the in-app chat. Host contact number is shown to tenant only in an emergency context (visible on tenant dashboard as "Emergency Contact" — not in public chat).
Admin actions on sensitive data (KYC approvals, account bans, listing takedowns) must be logged in an immutable audit table with: admin_id, action_type, target_entity_id, timestamp, and reason. Audit logs cannot be deleted — only read.

📋 Business Rules

Admin accounts cannot make bookings. Enforced at API level — booking creation endpoint returns 403 for admin role tokens.
A listing cannot go live without: minimum 5 photos, verified host KYC, at least one room type with pricing, and admin approval. Any listing failing these criteria stays in "Draft" status.
A booking cannot be confirmed without: user's KYC approved by admin, token payment successfully captured by Razorpay webhook, and available room count >0 for the selected room type. All three checks must happen server-side — not in the app.
Double booking prevention: when a booking is initiated, the room count is decremented immediately in a database transaction. If payment fails, the count is restored. This prevents two users from paying for the same room simultaneously.
Token refund policy: Full refund if host cancels. Full refund if user cancels more than 7 days before move-in. 50% refund if cancelled 3–7 days before move-in. No refund if cancelled within 3 days of move-in. These rules are applied in code automatically based on cancellation timestamp vs move-in date.
Walk-in bookings entered by hosts or agents must generate an SMS invite to the tenant within 60 seconds of entry — the SMS must contain the app download link and a unique pre-registration token that links the download to that specific booking.
