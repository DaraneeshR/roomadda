02 — Web ⇄ App SyncRoomadda · Website Blueprint v2.0

Section 02

Web ⇄ App
Sync Architecture

You asked for the website and app to be "linked" with the same pricing reflecting in both at the same time. The only correct way to do this is one shared backend that both clients read from. There is never a "website price" and an "app price" — there is one price, served to whoever asks.

🧠
The golden rule — Single Source of Truth
The website is not its own system with its own database. The website, the user app, the host app and the admin panel are four clients that all call the same REST/GraphQL API backed by the same PostgreSQL database. A host changes the rent once; that change is instantly true on the web, in the app, in search results, in the wishlist, and in the admin panel — because there is only one number stored anywhere.

How "same pricing at the same time" actually works

Host edits rent in the host portal (web or app). The API writes the new value to the single room_types record in PostgreSQL. No copy is made anywhere.
Cache is invalidated. A Redis cache key for that property is busted so stale prices can't survive. Major edits (rent change >20%) optionally route to admin re-approval before going live.
Every client re-reads the same record. The website's property page, the app's detail screen, the search index and the wishlist all fetch the new value on their next load — identical to the rupee.
Open sessions get a live nudge. Anyone currently viewing the property (web or app) receives a lightweight push/WebSocket event — "Price updated" — and the UI refreshes without a reload. This is how the change appears "at the same time" everywhere.
One backend serves both
  • Listings, pricing, availability, photos
  • User accounts, KYC, wishlist, bookings
  • Token & rent payments (Razorpay) + receipts
  • Reviews, ratings, trust-tag eligibility
  • Live counters (viewers, recent bookings)
  • Notifications (push, WhatsApp, email)
Each client renders its own way
  • Website: SEO-rendered (Next.js SSR) for Google
  • App: native-feeling React Native screens
  • Both: identical data, identical business rules
  • Booking rules enforced server-side, not per-client
  • Account is shared — log in once, same wishlist & bookings on both
  • Double-booking prevented at the database, for both

Deep linking & "redirect to the app"

You want the website to be able to hand a user over to the app. We do this with universal / app links + deferred deep links so the journey never breaks:

Universal Links (app installed)
Every property URL like roomadda.com/bangalore/koramangala/warmth-house-pg is registered as a universal link (iOS) / app link (Android). If the user already has the app, tapping that link on their phone opens the same property inside the app — not the browser. The web and app URL are the same string.
NEW
Deferred Deep Links (app not installed)
If the user taps "Continue in app" but doesn't have it, they go to the store, install, open — and land on the exact property they were viewing, with their search context preserved. Implemented via Firebase Dynamic Links (or Branch). This is what makes "redirect to the application" feel seamless rather than dumping them on a generic home screen.
NEW
Smart App Banner & QR
A dismissible top banner on mobile web ("Open in the Roomadda app") and a QR code on desktop checkout/success pages that resolves to the correct store by device. Tracked in GA4 as app_download_clicked with the source page.
NEW

Sync Rules — non-negotiable for the build team

No second database. The website must never store its own copy of listings or prices. It reads the same API as the app.
One price object. Rent, deposit, premium/private price and token are fields on one record. Web and app render the same fields — they never compute price differently.
Shared identity. A user logging in with the same mobile number on web and app is the same account — same wishlist, same bookings, same KYC status. OTP + Google Sign-In via the same auth service (Firebase + MSG91).
Server-side business rules. Availability checks, KYC gating, double-booking prevention and refund logic live in the backend, so web and app behave identically and can't drift.
Availability is live. When a room is booked on the app, the website's "rooms available" count drops on next fetch and via the live event — and vice versa.

08 — Trust Tags & BadgesRoomadda · Website Blueprint v2.0

Section 08

Trust Tags &
Badge System

You wanted OYO's "Wizard"-style tags, Flipkart "Assured", and Amazon's "Choice" — labels that instantly tell a nervous user "this one is safe / premium / popular." Below is the full Roomadda badge system: every badge, exactly how a listing earns it, and where it shows. Badges are earned by rules, never sold — that's what keeps them trustworthy.

🛡️
The principle that makes badges worth anything
A badge is a promise. If hosts could buy "RA-Assured," it would mean nothing and users would learn to ignore it. So every badge here is awarded automatically by the backend from real data (inspections, ratings, response times, booking volume) and re-evaluated on a schedule. "Featured" is the only paid/curated placement, and it is visually distinct from trust badges so the two are never confused.

The eight badges

✓ RA Verified
RA Verified
The baseline trust mark. Earned when: a Roomadda field agent has physically inspected the PG, the inspection report is approved by admin, and host KYC is verified. Without this, a listing cannot show any higher badge.
🛡️ RA-Assured
RA-Assured (your "Flipkart Assured")
A quality guarantee. Earned when: Verified + photos pass the quality bar (≥8 real, bright images) + amenities matched reality on inspection + host response rate ≥90% + zero unresolved escalations in 90 days. Signals "what you see is what you get."
⭐ RA Choice
RA Choice (your "Amazon's Choice")
The algorithm's top pick for a given search. Earned when: RA-Assured + rating ≥4.5 + high booking-conversion + fast response + good value for its area. Awarded per query context (e.g. "RA Choice for PG in Koramangala under ₹12K") — exactly like Amazon's Choice is keyword-specific.
💎 Luxury
Luxury
Premium-segment marker. Earned when: price in the top quartile for its area + premium amenities (AC, attached bath, housekeeping, etc.) + RA-Assured + rating ≥4.5. Drives the "Luxury PGs" category and intent landing page.
🧙 Wizard
Wizard (your OYO "Wizard")
A loyalty/elite tier for the very best hosts. Earned when: RA-Assured for ≥6 months + ≥20 completed stays + rating ≥4.6 + <5% cancellation + on-time meal-menu & service SLAs. Wizard hosts get priority ranking and a distinct gold-tinted badge.
🔥 Trending
Trending
Real-time popularity. Earned when: views & wishlist-adds in the last 7 days are in the top 10% for its area, or it was booked ≥3× this week. Time-boxed — drops off automatically when momentum fades. Pure honesty, recomputed hourly.
⚡ Instant Book
Instant Book
Convenience signal. Earned when: the host has enabled instant booking and has live availability — confirms on payment with no 24-hour approval wait. Filterable.
📣 Featured
Featured (paid / curated — NOT a trust badge)
The only purchasable placement. Set by: admin, with a start/end date. Always labelled "Featured" or "Ad" and styled differently from trust badges, so users are never misled. Featured listings still must be at least RA Verified to appear.

09 — Live Social ProofRoomadda · Website Blueprint v2.0

Section 09

Live Social Proof
& Urgency Engine

You asked for live numbers — how many people are watching a property right now, how many booked it in the last 5 days / week / month. This is one of the strongest conversion levers OYO and MakeMyTrip use. Here is the full engine, plus the rules that keep every number true — fake urgency destroys trust the moment a user catches it.

⚠️
Honesty rule — every number must be real
No invented "27 people are looking!" counters. Each figure below is computed from actual events in our own analytics. If a property genuinely has low activity, we simply don't show that widget for it rather than faking a number. A counter that's caught lying once poisons trust in the whole site.

The live-proof widgets

"👁 X people viewing now"
A live count of distinct sessions currently on this property page (web + app combined). Computed from: active sessions tracked in Redis with a short TTL (e.g. a session counts as "viewing" for ~2–3 minutes after its last heartbeat). Shown on the property page and, as a compact "X viewing", on hot cards. Only displayed when the real count ≥ a floor (e.g. ≥3) so it never looks pathetic or fake.
  • Updates live via WebSocket / short polling
  • Counts unique sessions, not page refreshes
  • Hidden when below the floor — never padded
CORE
"🗓 Booked Y times in the last 5 days / week / month"
